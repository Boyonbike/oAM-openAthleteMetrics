❯ # Driver Authoring Guide Audit (Read-Only)                                    
                                                                                
  This is a diagnostic session. Produce findings only — do not edit the guide   
  or any code.                                                                  
                                                                                
  ## Context                                                                    
                                                                                
  oAM's BLE device driver system: drivers are JSON manifests with embedded      
  base64-compiled WASM modules, executed via Chicory (pure-Java WASM            
  interpreter). No built-in Kotlin drivers — plugin-only. Reference device:     
  Hume Band J2208. Drivers are hand-authored in WAT (WebAssembly Text);         
  AssemblyScript is the noted fallback if WAT becomes unwieldy.                 
                                                                                
  ## Task                                                                       
                                                                                
  Locate the driver authoring guide in this repo (search docs/, README files,   
  and any `*driver*guide*` or `*authoring*` filenames) and locate the actual    
  driver runtime code (manifest schema/parser, Chicory host bindings, WASM      
  invocation layer, and any existing driver implementations, including the Hume 
  Band J2208 reference driver).                                                 
                                                                                
  Compare the guide against the current code and report every place they've     
  drifted. Specifically check:                                                  
                                                                                
  1. **Manifest schema** — do the fields, types, and structure the guide        
  documents match what the manifest parser actually reads/validates?            
  2. **Host function interface** — do the function names, parameter             
  order/types, and return types the guide lists match what's actually exposed   
  to WASM modules in the Chicory bindings?                                      
  3. **Required lifecycle functions** — does the guide correctly list every     
  function a driver must export (e.g. init, parse/record handlers,              
  `buildSyncCommands`), and match their actual required signatures?             
  4. **Command sequencing** — does the guide correctly explain that the driver  
  owns command sequencing via `buildSyncCommands`, and that `awaitEndOfStream`  
  (not fixed delays) is the correct mechanism for pacing? Flag if the guide is  
  silent on this or describes it differently.                                   
  5. **Multi-record packet handling** — does the guide warn authors that        
  handlers like `$do_hrv` (and structurally similar ones) must stride across    
  all concatenated records in a packet, not just read a fixed offset? This has  
  been a real bug source — confirm the guide documents it.                      
  6. **WASM memory layout constraints** — does the guide document the linear    
  memory layout risk (large input data at offset 16 can overwrite static        
  string/table regions, e.g. around `0xD800`) and the `WASM_SAFE_INPUT_BYTES`   
  chunking requirement for large sessions?                                      
  7. **Example/reference driver accuracy** — if the guide includes a worked     
  example or references the Hume Band J2208 driver, confirm the example still   
  compiles/matches the current manifest schema and host interface.              
  8. **Anything else** — flag any other guide claim (API name, opcode format,   
  build/compile step for WAT→WASM, testing instructions) that no longer matches 
  the code.

● Driver Authoring Guide Audit — Findings

  I compared docs/DRIVER_AUTHORING_GUIDE.md (1880 lines) against the live
  runtime (WasmDriverEngine.kt, BleEngine.kt, DriverRegistry.kt,
  ManifestValidator.kt, ParsingConfig.kt, DeviceSyncProcessor.kt,
  DeviceReprocessor.kt, MetricRouter.kt, EndOfStreamStrategy.kt) and the actual
  reference driver (Driver Builds/Hume Band 1/HumeBandDriver.json +
  hume_band.wat). The drift is severe: the guide documents an architecture that 
  has been superseded, and the reference driver itself doesn't conform to what
  the guide teaches.

  ---
  BREAKING

  1. The guide's entire per-notification parsing model 
  (parseMetrics/parseSleep/parseActivity) is dead code — never invoked by the 
  live engine.
  - Guide: "4. Parsing" (L69-86), "Memory Layout" (L1029-1066), "Function
  Signature" (L1068-1078), "Call Sequence (per notification)" (L1083-1093), all
  of "JSON Output Schemas" (L1095-1204) — describes the app calling these three
  exports once per BLE notification.
  - Code: WasmDriverEngine.callParse() (ble/wasm/WasmDriverEngine.kt:403)
  implements this exactly, but is never called anywhere in app/src/main/java
  (verified by grep). BleEngine.handleNotification() (ble/BleEngine.kt:376-445)
  only buffers each packet into sessionCache; all parsing happens in
  BleEngine.triggerSync() (:479-507) via DriverRegistry.parseSession() →
  WasmDriverEngine.parseSession() (ble/wasm/WasmDriverEngine.kt:116), one bulk
  call with every buffered frame. A driver that follows the guide's documented
  contract (exports only parseMetrics/parseSleep/parseActivity, no parseSession)
  loads successfully but produces zero data, silently.

  2. parseSession — the mechanism every real code path and the reference driver 
  actually use — is undocumented.
  - WasmExports (ble/driver/ParsingConfig.kt:53-64) has a parseSession: String?
  field whose doc comment says it "Replaces per-notification exports when
  present." ManifestValidator (ManifestValidator.kt:90) accepts parseMetrics or
  parseSession, not parseMetrics alone as the guide's schema table states
  (L1004-1011, no parseSession row).
  - HumeBandDriver.json declares "exports": {"parseSession": "parseSession", 
  "buildSyncCommands": "buildSyncCommands"} — no parseMetrics. Its compiled
  hume_band.wat exports only parseSession/buildSyncCommands (lines 957, 1272).
  - parseSession's actual input isn't raw bytes at a fixed offset — it's a JSON
  array [{"characteristic","opcode","bytes":"<base64>"}...]
  (WasmDriverEngine.buildFramesJson, :571-581), one entry per reassembled packet
  across the whole session. This schema appears nowhere in the guide.

  3. The guide's "specVersion 2 buildSyncCommands" zero-argument signature would
  trap if implemented — the engine always calls the two-argument form.
  - Guide (L860-919) documents (func (result i32)), no parameters, reading a
  metadata block the host pre-writes.
  - Code: callBuildSyncCommandsWithContext() (WasmDriverEngine.kt:517-568)
  always calls exportFn.apply(offset, len) — the two-i32-argument signature the
  guide separately documents under "specVersion 3" (L1338+). There is no code
  path that ever calls a zero-arg buildSyncCommands. Following the guide's "spec
  v2" section produces a WASM function with the wrong export arity.

  4. "Raw replay" / processFromRaw() describes a deleted method; the real 
  implementation is a different class with different semantics.
  - Guide (L133-149, and L553-610 "Driver Versioning...") states
  DeviceSyncProcessor.processFromRaw() re-parses raw_device_data for a session
  and calls MetricRouter.routeAll().
  - DeviceSyncProcessor.kt:244: // REMOVED: interrupted-sync-recovery — 
  processFromRaw() deleted. The feature now lives in
  DeviceReprocessor.reprocess(device, since, onProgress)
  (ble/sync/DeviceReprocessor.kt:51), windowed by time (since: Instant) not
  session ID, uses parseSession (not per-packet parsing), and writes via
  MetricRouter.routeAllForceReplace() (MetricRouter.kt:188) —
  MetricRouter.routeAll() does not exist anywhere in the codebase.

  5. specVersion guidance is meaningless for the one code path that's actually 
  live, and the reference driver uses an undocumented value.
  - Guide (L1808): "Only \"1\", \"2\", and \"3\" produce defined behaviour.
  Other values fall back silently to spec v1 layout." HumeBandDriver.json
  declares "specVersion": 4 — by the guide's own rule this should mean broken
  spec-v1 fallback, but parseSession's input writer (callParseSessionBytes,
  WasmDriverEngine.kt:451-483) never checks specVersion at all; it
  unconditionally writes to offset 16. specVersion only gates the dead
  callParse() path (finding 1) — it's vestigial for every real driver today.

  6. HumeBandDriver.json's specVersion is an unquoted JSON number (4), while the
  schema type is String — likely fails to parse.
  - WasmDriverManifest.specVersion: String (WasmDriverManifest.kt:54), decoded
  via Json { ignoreUnknownKeys = true } (DriverStorage.kt:18, isLenient defaults
  to false). kotlinx.serialization's default (non-lenient) Json rejects an
  unquoted numeric literal where a String is expected. I could not execute the
  toolchain in this sandbox to get a 100%-certain repro, but this is standard,
  well-documented kotlinx.serialization behavior — worth confirming with a quick
  unit test loading the actual file, since if correct, the shipped reference 
  driver fails to load in the app at all, silently caught and logged by
  DriverStorage.loadAllDrivers()'s catch block.

  ---
  Stale / misleading (not immediately fatal, but wrong)

  7. Live-sync description of MetricRouter.route() timing is inaccurate.
  Guide (L110-124): routing happens "on each incoming notification as packets
  arrive." Code: routing (routeReading) only runs inside triggerSync()
  (BleEngine.kt:484-497), after the whole session's parseSession call completes
  — handleNotification() does no routing.

  8. Undocumented plausibility filter silently drops readings.
  Guide's reading-validation rules (L157-162) list only NaN/Infinite, timestamp
  bounds, blank unit, unknown type. Code (MetricRouter.implausibleDeltaReason(),
  MetricRouter.kt:202-226) additionally drops DELTA-mode STEPS (>400/min,
  scaled by syncIntervalMs) and ACTIVE_CALORIES (>30 kcal/min) deltas, and any
  negative delta — logged only via Timber.w, never surfaced. Not mentioned
  anywhere in Validation Rules, Deduplication, or the Steps/Calories
  Accumulation Mode sections.

  9. Multi-record striding is implemented correctly but undocumented as a 
  required pattern.
  hume_band.wat:590-631 ($do_hrv) correctly loops in fixed 15-byte strides
  across the whole decoded buffer, bounded by $rawlen. The guide never mentions
  record striding, concatenated multi-record packets, or $do_hrv — despite this
  being called out as a real historical bug source. Current implementation is
  correct; the guide gives a new-driver author no way to know this pattern is
  required.

  10. 0xD800 memory-collision risk and WASM_SAFE_INPUT_BYTES chunking are absent
  from the guide — but the underlying risk is actually resolved, not live.
  WasmDriverEngine.kt:603-607: static WASM data "previously started at 0xD800...
  they've since moved to their own page (0x40000+)," so large input "no longer
  risks corrupting them." WASM_SAFE_INPUT_BYTES = 50_000 is now just a
  conservative JSON-payload chunk size for parseSession (splitFrameChunks,
  :177-184). Low severity — nothing in the guide is actively wrong here, but
  it's silent on the fact that a large session may be split across multiple
  parseSession calls.

  ---
  Not drifted (verified consistent, for completeness)

  - The syncCommands static command types (WRITE/ENABLE_NOTIFY/DELAY),
  awaitReply, and all seven awaitEndOfStream strategies (FIXED_OFFSET_BYTE,
  SENTINEL_PACKET, IN_STREAM_TERMINATOR, RECORD_COUNT, EXPLICIT_EVENT,
  QUIET_PERIOD, CUSTOM) match EndOfStreamStrategy.kt/EndOfStreamStrategyFactory
  field-for-field, including fallback-to-TimeoutOnly behavior and the
  SentinelPacket pass-through exclusion.
  - ManifestValidator's CUSTOM-strategy wasmExport check and intra-/cross-driver
  signature-collision checks match the guide's Validation Rules table.

  ---
  Bottom line: the guide's core "Writing a WASM Driver Module" chapter and its
  worked example describe a parsing contract
  (parseMetrics/parseSleep/parseActivity, per-notification calls, spec-v2
  zero-arg buildSyncCommands) that the engine no longer executes, while omitting
  the parseSession-based contract that the reference driver, DriverRegistry,
  BleEngine, and DeviceReprocessor all actually use. An author (human or AI)
  following this guide today would build a driver that loads but silently never
  parses data. The parseSession schema, its base64 frame format, and the correct
  buildSyncCommands two-argument signature need to be documented as the primary
  (only) path.
