  Findings Report: BLE Multi-Device Sync & Background Scheduling Recon

  Facts sessions 5 & 6 must embed

  - Orchestrator seam: No queue/orchestration abstraction exists anywhere. A
  sequential-device orchestrator is a new component sitting above BleEngine,
  driving fun connectToDevice(bleAddress: String, manifest: WasmDriverManifest)
  at BleEngine.kt:237 one device at a time, observing val connectionState: 
  StateFlow<BleConnectionState> at BleEngine.kt:188 for a terminal state, then
  calling fun disconnect() at BleEngine.kt:325 before advancing.
  connectToDevice()/connect() have no internal reentrancy gate — only callers
  (autoConnectOnStartup, DevicesViewModel) currently self-gate. An orchestrator
  must supply its own gate, or calling it again mid-cycle will clobber
  activeGatt/activeManifest/activeDeviceAddress and orphan the previous
  BluetoothGatt.
  - Reassembly-buffer-clear guarantee: reassemblyBuffers (BleEngine.kt:131,
  keyed by characteristic UUID only, not per-device) is cleared at disconnect()
  (:346), triggerSync() (:587), unconditionally at the top of every connect()
  (:678), and in dispatchPostStreamParse() (:1388). Sequential runs cannot leak
  packets between devices — provided the orchestrator never re-enters
  connectToDevice() before the prior cycle's disconnect/parse has actually
  completed (same caveat as above).
  - BleSyncService notification seam: buildNotification() at
  BleSyncService.kt:51-59 currently emits a static "Syncing device…" string;
  onStartCommand's intent param is unused (line 35). This is the seam for a
  future "Syncing X (n of m)" notification, but it needs a data path added first
  (Intent extras, or the service observing BleEngine state itself).
  - WorkManager registration pattern: One-time work uses enqueueUniqueWork +
  ExistingWorkPolicy (AppStartupWorker.kt:39-45); periodic uses
  enqueueUniquePeriodicWork + ExistingPeriodicWorkPolicy
  (WidgetRefreshWorker.kt:42-49, 30-min interval). Hilt wiring:
  AthleteDataApplication implements Configuration.Provider, injects
  HiltWorkerFactory (AthleteDataApplication.kt:94-97); default WorkManager
  initializer is removed in AndroidManifest.xml:142-151. No existing Worker uses
  Constraints — a background-sync Worker would be the first. No periodic 
  BLE-sync Worker exists today (confirmed by grep).
  - minSdk/targetSdk: minSdk = 26, targetSdk = 36, compileSdk = 37 —
  app/build.gradle.kts:11,15,16 (verified directly). targetSdk 36 already
  enforces Android 12+ BLE runtime permissions and Android 14
  foreground-service-type (connectedDevice, already declared).
  - Startup-trigger site: bleEngine.autoConnectOnStartup() fires exactly once,
  unconditionally, from MainActivity.onCreate() at MainActivity.kt:34 — not from
  Application.onCreate() or any Worker. A background scheduler must coordinate
  with this Activity-driven trigger to avoid double-firing.

  1. Single-sync lifecycle (end to end)

  State fields — confirmed singular (verified directly against source):
  - activeManifest: WasmDriverManifest? — BleEngine.kt:112
  - activeDeviceAddress: String? — BleEngine.kt:113
  - activeGatt: BluetoothGatt? — BleEngine.kt:175

  One @Singleton BleEngine instance holds exactly one of each — no per-device
  collections.

  Call sequence for one full sync:
  1. connectToDevice(bleAddress, manifest) (:237) → connect(device, manifest, 
  resetRetries = true) (:246).
  2. connect() (:650-693): clears accumulators + reassemblyBuffers.clear()
  (:678), sets Connecting state (:686), device.connectGatt(...) (:688).
  3. onConnectionStateChange (:698) → STATE_CONNECTED → gatt.requestMtu(...)
  (:705).
  4. onMtuChanged (:738) → gatt.discoverServices() (:747).
  5. onServicesDiscovered (:751) → builds notify queue →
  enableNextNotification() (:771).
  6. enableNextNotification() (:997) drains queue → beginSyncCommandExecution()
  (:1004).
  7. beginSyncCommandExecution() (:1049) sets Syncing (:1052) →
  executeNextSyncCommand() (:1065).
  8. executeNextSyncCommand() (:1114) walks Write/EnableNotify/Delay commands,
  arming awaitReplyDeferred/awaitEndOfStreamDeferred (:1176-1214).
  9. Notifications arrive via onCharacteristicChanged (:807, :850) → checked
  against awaitEndOfStreamStrategy (:826, :869) → forwarded to
  notificationChannel (:137).
  10. A dedicated consumer coroutine (init, :212-218) drains the channel and
  calls handleNotification(characteristicUuid, bytes) (:412) — appends into
  reassemblyBuffers[uuid] (:427), detects completion when a fragment is shorter
  than negotiatedMtu - 3 (:431), persists raw packets immediately (:452-456).
  11. End-of-stream detection: (a) driver-declared awaitEndOfStream resolved in
  onCharacteristicWrite's aesDeferred branch (:932-982), setting
  endOfStreamReceived = true (:977); (b) fallback quiescence/silent-sync timers
  when no strategy is declared (:467 gate, :1130).
  12. All commands done + EOS received → dispatchPostStreamParse() (:1360):
  closes GATT (:1377-1379), clears reassemblyBuffers (:1388), parses
  sessionCache, enqueues DailySummaryWorker, sets SyncComplete (:1453).
  Passive-stream drivers (no EOS) stay Connected until manual disconnect()
  (:325) or acknowledgeSyncComplete() (:363).
  13. Re-sync of an already-connected device goes through triggerSync() (:506)
  directly, clearing reassemblyBuffers again (:587).

  startScan() gating (:261-323): line 264 returns early unless current state is
  Idle/Error/GattCacheError — scanning is blocked while
  connected/connecting/syncing. connectToDevice()/connect() themselves have no 
  equivalent internal gate — this is the key gap an orchestrator must fill.

  2. Sync triggering / queuing

  (a) Startup: MainActivity.onCreate() → autoConnectOnStartup(). This picks the
  most-recently-synced/seen device (maxByOrNull { lastSyncMs ?: lastSeenMs ?: 0L
  }, :230) — there is no "primary device" concept in the Device model (only
  lastSeenMs/lastSyncMs/lastBatteryPct). Session 5's "primary first" ordering
  needs a new field.

  (b) Manual tap: DevicesViewModel.onSyncTapped() → bleEngine.startSync(),
  documented as fire-and-forget on the engine's app-scoped coroutine scope — not
  awaitable/chainable by a caller.

  Auto-sync-on-connect: a separate init-block collector (:199-208) calls
  triggerSync() on every Connecting → Connected transition regardless of UI
  screen.

  No existing queue/orchestration abstraction (confirmed by repo grep —
  ble/sync/ only contains single-device helpers: DeviceSyncProcessor,
  DeviceReprocessor, SleepMerger, SyncSummary, SyncValidator, MetricRouter).

  Exact seam: wrap connectToDevice() (:237) + observe connectionState (:188) to
  a terminal state + call disconnect()/acknowledgeSyncComplete() — this must
  live above BleEngine (new orchestrator class or Service), since BleEngine's
  API and state are single-device by design.

  3. Reassembly buffer safety

  reassemblyBuffers: MutableMap<String, ByteArray> (:131) is keyed by
  characteristic UUID only — one map per engine singleton, not per-device.
  Verified clear sites: disconnect() (:346), triggerSync() (:587), connect()
  (:678, unconditional on every connection attempt including retries),
  dispatchPostStreamParse() (:1388). Safe for sequential runs as long as the
  orchestrator never re-enters connectToDevice() before the prior device's
  disconnect/parse has completed.

  DeviceReprocessor.kt has no reassembly buffer — it reconstructs frames from
  already-persisted raw rows and is documented as "must only be called when BLE
  is idle" (offline reprocessing, not live-stream).
