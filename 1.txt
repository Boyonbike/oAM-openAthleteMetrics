     Add "Cancel" to the Connecting/Syncing/Parsing banner (styled like the 
     existing "Stop")

     Context

     The Devices page shows a banner (BleBanner in DevicesScreen.kt) that
     changes content based on BleConnectionState. Today only the Scanning phase
     ("Scanning for devices...") has a cancel affordance — a plain clickable
     Text("Stop", ...) next to the label, wired to BleEngine.cancelScan(). The
     Connecting, Syncing, and Parsing phases show only a label + progress bar,
     with no way to back out. The user wants a "Cancel" button added to those
     three phases, in the same visual slot and style as "Stop", that reliably
     halts the operation:

     - Stops the sync/parse in progress.
     - Discards any data collected or parsed from the device during that attempt
     — nothing partial should land in the database.
     - If the BLE connection is already established (device is genuinely
     connected), cancelling must not disconnect it — only the sync/parse
     activity stops.
     - If cancelled during Connecting (before any GATT link exists), the app
     must not proceed to connect.

     Investigation of BleEngine.kt (the real state machine — DevicesViewModel is
     a thin pass-through) found:
     - The Connecting phase has no live GATT link yet — cancelling it is safe to
     implement by reusing the existing disconnect() path, which already tears
     down an in-progress connectGatt() attempt and lands on Idle (via a brief
     transient Disconnected), without ever reaching Connected.
     - The Syncing phase (executeNextSyncCommand()) is driven recursively
     through Android BLE GATT callbacks, not a single coroutine — cancellation
     must be a cooperative flag, not a Job.cancel().
     - The Parsing phase runs the actual data write in a single
     scope.launch(Dispatchers.IO) { ... } block that calls MetricRouter.route()
     once per reading, immediately, with no transaction — so a naive cancel
     could leave a partial set of readings permanently in the database. Some
     metric tables (e.g. STEPS/ACTIVE_CALORIES in ABSOLUTE mode) do a
     delete-then-insert per reading, making a mid-loop interruption doubly
     risky. The metric reading tables have no sync_session_id column, so there's
     no way to delete "just this session's rows" after the fact — the only
     reliable fix is to prevent the writes from committing at all via a DB
     transaction that rolls back on cancellation.
     - RawDeviceDataRepository.deleteForSession(syncSessionId) already exists
     but is dead code (never called) — it's the natural hook for discarding raw
     bytes written during a cancelled Syncing/Parsing attempt.
     - MultiDeviceSyncOrchestrator.isTerminal() doesn't currently treat Idle as
     terminal, which would make it wait up to 5 minutes if a cancel during
     EOS-driver Parsing lands the engine on Idle.

     Approach

     1. data/model/SyncStatus.kt

     Add a CANCELLED enum constant. Persisted via Converters.kt's
     .name/.valueOf() — no Room migration, no exhaustive when anywhere breaks
     (verified: only non-exhaustive when {} branches reference this enum).

     2. ble/BleEngine.kt (bulk of the work)

     - Inject AppDatabase and SyncSessionRepository into the constructor (both
     already Hilt-bound singletons, same as DeviceSyncProcessor already does).
     - Add @Volatile private var cancelRequested = false and private var 
     activeSyncJob: Job? = null. Reset cancelRequested = false in connect()
     alongside the existing userDisconnecting = false.
     - New public fun cancelSync(), branching on _connectionState.value:
       - Connecting → call the existing disconnect() directly. It only needs
     activeDeviceAddress != null (true here), doesn't inspect state, and already
     produces the right outcome (never reaches Connected).
       - Syncing → set cancelRequested = true; cancel
     retryJob/silentSyncTimeoutJob/writeAckTimeoutJob/quiescenceJob; null the
     awaitReplyDeferred/awaitEndOfStreamDeferred fields (same guard pattern the
     callbacks already use); do not touch activeGatt; delete raw session data
     and mark the SyncSession row CANCELLED (new markSyncSessionCancelled()
     helper, fire-and-forget on IO, wrapped in runCatching so it never blocks
     the UI transition); clear sessionCache/pendingMetrics/pendingSleep/pendingA
     ctivities/affectedDates/reassemblyBuffers; then transition state
     synchronously — Connected(address, driverName, 0, true) since GATT is
     always open in this phase (mirrors the existing open-GATT check in
     acknowledgeSyncComplete()).
       - Parsing → ownership handoff, not synchronous cleanup: set
     cancelRequested = true, cancel retryJob, and call activeSyncJob?.cancel().
     The in-flight parse coroutine is the sole owner of finishing cleanup once
     it observes the cancellation (see below) — this avoids two writers racing
     on _connectionState.
       - Other states → no-op.
     - executeNextSyncCommand(): add a cancelRequested check at the very top
     that returns immediately, halting the recursive command chain. No other
     callback needs an individual check.
     - scheduleRetry(): add a guard at the top — if cancelRequested, clear
     activeManifest/activeDeviceAddress/activeDeviceId, reset retryCount, set
     Idle, and return (instead of scheduling a reconnect). Covers the narrow
     race where a write/GATT error arrives the same tick as a cancel.
     - triggerSync() (passive/streaming-driver path, GATT stays open through
     parsing) and dispatchPostStreamParse() (EOS-driver path, GATT already
     closed before Parsing state is even entered):
       - Wrap the existing per-reading for (vr in readingResults) { 
     routeReading(...) } loop in appDatabase.withTransaction { }. Room's suspend
     DAO calls already check coroutine cancellation, so a plain Job.cancel()
     triggers a CancellationException at the next DB write and Room rolls back
     the whole transaction atomically — no manual "isCancelled()" polling
     needed.
       - Capture the launching coroutine into activeSyncJob at all three launch
     sites: startSync(), the init block's auto-trigger-on-Connected collector,
     and dispatchPostStreamParse()'s scope.launch(Dispatchers.IO) { ... }.
       - Add a catch (e: CancellationException) block (before the existing
     generic catch (e: Exception)), wrapped in withContext(NonCancellable) { }
     so cleanup itself can't be re-cancelled: call markSyncSessionCancelled(),
     clear sessionCache, and transition state using the same open-GATT check as
     the Syncing branch (Connected(...) if activeGatt != null, else clear the
     active-device fields and go Idle). In dispatchPostStreamParse()'s case this
     always lands Idle since GATT is already closed by the time Parsing starts;
     written generically for symmetry with triggerSync().
     - New private suspend fun markSyncSessionCancelled(sessionId: Long):
     runCatching { rawDeviceDataRepository.deleteForSession(sessionId) }, then
     runCatching { syncSessionRepository.getById(sessionId)?.let { 
     update(it.copy(status = SyncStatus.CANCELLED, endedAt = Instant.now())) } }
     — both failures logged and swallowed so a cancellation always completes
     its state transition even if this bookkeeping fails.

     3. ble/sync/MultiDeviceSyncOrchestrator.kt

     Add is BleConnectionState.Idle -> true to isTerminal(). Confirmed safe:
     connectToDevice() synchronously moves state off Idle via its tryAcquire()
     gate before the orchestrator starts observing, so a stale pre-connect Idle
     is never misread as this device's outcome. With this fix, cancelling one
     device mid-auto-sync-run lets the orchestrator move on to the next queued
     device within seconds instead of waiting out the 5-minute timeout backstop.
     No other orchestrator change needed — finishDevice() already
     unconditionally disconnects between devices for any non-SyncComplete
     outcome (including a healthy quiescent Connected), so
     cancel-while-connected during a multi-device run isn't a new case, it's the
     same "disconnect to move to the next device" behavior that already exists.

     4. ui/devices/DevicesViewModel.kt

     Add fun onCancelSync() { bleEngine.cancelSync() }, next to the existing
     onScanCancelled().

     5. ui/devices/DevicesScreen.kt

     - Add an onCancelSync: () -> Unit parameter to BleBanner, wired at the call
     site to viewModel::onCancelSync.
     - In the Connecting, Syncing, and Parsing branches of BleBanner's when 
     (state), replace the bare label Text with a Row matching the existing
     Scanning branch's layout exactly: label Text with Modifier.weight(1f), then
     Text("Cancel", style = TypographyTitle, color = 
     MaterialTheme.colorScheme.primary, modifier = Modifier.clickable(onClick = 
     onCancelSync)). Same TypographyTitle style and colorScheme.primary tint as
     "Stop" — no new component needed.

     Verification

     - Build and run the app; connect to a real (or test) BLE device.
     - Cancel during Connecting: tap Cancel immediately after tapping a
     discovered device — banner should disappear, device never reaches
     Connected, no lingering scan/connect state.
     - Cancel during Syncing (passive/streaming driver, link survives sync): tap
     Cancel — banner disappears, device tile shows Connected (not
     disconnected), a subsequent manual "Sync" works normally, and
     raw_device_data / typed metric tables show nothing new from the cancelled
     attempt (check via Room DB inspector or logs); sync_sessions table shows a
     CANCELLED row for that attempt.
     - Cancel during Parsing, EOS driver (GATT already closed by the time
     Parsing starts): tap Cancel — banner disappears, engine settles on Idle, no
     partial reading rows exist for that attempt. Specifically test with a
     STEPS or ACTIVE_CALORIES ABSOLUTE-mode driver to confirm the transaction
     rollback doesn't leave a day's data deleted-but-not-reinserted.
     - Cancel during Parsing, passive/streaming driver (GATT stays open): tap
     Cancel — banner disappears, device tile shows Connected.
     - Cancel mid multi-device auto-sync run: trigger auto-sync across 2+
     devices, cancel the one currently active — orchestrator should proceed to
     the next device within a few seconds, not hang until the 5-minute timeout.
     - Confirm the existing "Stop" button (Scanning phase) and "Dismiss"/"Retry"
     buttons (SyncComplete/Error/GattCacheError) are untouched and still work.
