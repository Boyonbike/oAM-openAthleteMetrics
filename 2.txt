● Investigation Report — Hume Band awaitEndOfStream wiring, real-device gap

  Verdict up front: this is NOT a wiring/build-artifact gap. Every layer I 
  checked — .wat source, both compiled .wasm binaries, the JSON manifest, and 
  the Kotlin strategy factory/arming code — is uniform across all six opcodes. 
  The ~30s stalls on 0x55/0x52/0x53 point to an open question about real-device 
  behavior, not a code defect.

  2. Address vs. template

  The shared IN_STREAM_TERMINATOR template lives at (data (i32.const 0x40D00) 
  ...) (line 230), 157 bytes, content ","awaitEndOfStream":{...,"strategy":"IN_S
  TREAM_TERMINATOR","params":{"matchOpcode":true,"terminatorSuffix":"0xFF"}...}.
  The dead SENTINEL_PACKET block is at 0x409F5ish inside the 0x40900 segment
  (comment-labeled [DDF5], 147 bytes), unreferenced anywhere in
  $buildSyncCommands.

  All six opcodes point at (a), the new shared template — none point at the dead
  SENTINEL_PACKET address or anything else. This refutes the hypothesized
  2-vs-4 split at the source level.

  3. JSON manifest independent encoding

  HumeBandDriver.json's parsing block contains only mode: "WASM", wasmBase64,
  and two export names (parseSession, buildSyncCommands). There is no static 
  syncCommands array and no per-opcode strategy/terminator config — the entire
  command list, including every awaitEndOfStream block, is generated at runtime
  purely by the WASM export. So there's nothing at the JSON layer that could
  diverge; it's necessarily as uniform as the WASM output.

  5. Runtime strategy resolution

  - EndOfStreamStrategyFactory.from() (EndOfStreamStrategy.kt:272-293) parses
  "IN_STREAM_TERMINATOR" + matchOpcode:true + terminatorSuffix:"0xFF" into
  EndOfStreamStrategy.InStreamTerminator(matchOpcode=true, 
  terminatorSuffix=[0xFF]) — pure function of the JSON, no opcode-specific
  branching exists.
  - BleEngine.executeNextSyncCommand() (BleEngine.kt:1077-1096) arms a fresh
  strategy instance per command, deriving opcode = bytes.firstOrNull() from
  cmd.bytes — i.e. the current command's own write payload, freshly computed
  each iteration (BleEngine.kt:1062,1086-1087). No shared/stale state across
  commands.
  - onCharacteristicChanged (BleEngine.kt:743-763, 786-806) calls
  strategy.onNotification(bytes, elapsedMs) on raw, per-callback notification
  bytes, before any app-level reassembly — identical code path regardless of
  characteristic/opcode.

  Today, 0x55/0x52/0x53 are armed with the exact same
  InStreamTerminator(matchOpcode=true, "0xFF") object type and parameters as
  0x66/0x56/0x65. There is no special-casing anywhere in this path.

  Additionally, WasmHumeBandBuildSyncCommandsTest.kt (already present in the
  working tree, added last session) drives the real compiled hume_band.wasm
  end-to-end and asserts all six opcodes emit
  IN_STREAM_TERMINATOR/matchOpcode:true/terminatorSuffix:"0xFF"/timeoutMs:30000
  identically. I could not execute it here (JAVA_HOME/java unavailable in this
  environment, so ./gradlew failed before touching any file), so I'm not
  claiming its pass/fail status — but its assertions match exactly what I
  independently derived from the raw bytes.

  6. What would confirm/refute the remaining hypothesis

  Since source, artifacts, manifest, and runtime code are all uniform, the only
  place left for a real 2-vs-4 split is device-side behavior. What's needed: a
  capture of the last N raw bytes of the final notification for 0x55, 0x52, and 
  0x53 on the actual notify characteristic, at the same fidelity as whatever
  showed 0x66/0x56 ending in [opcode, 0xFF]. Specifically check:
  - Does the final 0x55 notification's tail equal 55 FF? Same for 52 FF (0x52)
  and 53 FF (0x53)?
  - If not, what does it actually end in — e.g. extra trailing bytes after
  [opcode, 0xFF] (a checksum, a record count, padding), or is the terminator
  split across two separate BLE notification callbacks (last fragment
  smaller/larger than expected), or is a completely different byte value used
  for the trailing marker for these three opcodes?

  docs/core-systems.md:176-180 documents a separate reassembly mechanism
  ("Short-Packet Terminal": a notification < negotiatedMtu - 3 bytes is treated
  as buffer-complete for parseSession purposes) — this operates independently of
  and after the awaitEndOfStream strategy check, so it can't explain a stall in
  awaitEndOfStream itself, but it's worth keeping in mind if 0x55/0x52/0x53's
  payloads are large enough to span many MTU-sized fragments: it raises the
  possibility the device paces/terminates those longer multi-record streams
  differently than the short single-fragment 0x66/0x56/0x65 responses.

  7. Summary verdict

  Not a wiring or build-artifact gap. Tasks 1–5 all show full uniformity:
  identical $wmem addresses/lengths in the current .wat for all six opcodes
  (task 1–2), no independent JSON-level config to diverge (task 3),
  byte-identical artifacts across all three locations that reproduce exactly
  from the current source via wat2wasm (task 4), and identical,
  non-special-cased Kotlin parsing/arming/detection code (task 5). The next step
  is a targeted real-device capture of the exact final-notification tail bytes
  for 0x55, 0x52, and 0x53 (per task 6) — that byte-level evidence, not another
  code read, is what will settle whether those three opcodes actually append
  [opcode, 0xFF] the same way SpO2/HRV/Temp do.
