  - Reads the stage count from base+9, computes ts_start = $bcd_ts(base+3)

  routeReading() for each parsed reading      ← stages SLEEP_STAGE rows AND

  finally block at BleEngine.kt:1246–1251 fires after syncProcessor.process()

  ZoneId.systemDefault() is used. Bug 2 is fixed.

  The time-window filter in getPendingSleepStages is wrong

  SleepStagePromoter.promote() calls (SleepStagePromoter.kt:40–45):
  stagingRepository.getPendingSleepStages(
      source = DataSource.DEVICE,
      driverId = driverId,
      startMs = syncWindowStartMs,
      endMs = syncWindowEndMs,
  )

  Where syncWindowStartMs = result.syncStartedAt.toEpochMilli() = the epoch-ms
  when BleEngine.connect() set syncStartedAt = Instant.now() (i.e., when the
  morning BLE connection was initiated — e.g., 07:00 today).

  The DAO query (MetricReadingStagingDao.kt:177–192):
  WHERE metric_type = 'SLEEP_STAGE'
    AND source = :source
    AND driver_id = :driverId
    AND recorded_at >= :startMs       ← sync start time (e.g., 07:00 today)
    AND recorded_at < :endMs          ← sync end time (e.g., 07:02 today)

  SLEEP_STAGE rows have recorded_at = historical sleep stage start time (Stage
  1: WAT sets recordedAtMs = ts_start + span_start * 60000 = the BCD-decoded BLE
  timestamp of the sleep stage). For a typical overnight sleep session, every
  stage's recorded_at is between 22:00 last night and 06:00 this morning.

  The condition recorded_at >= syncWindowStartMs evaluates to:
  ~22:00 last night >= 07:00 this morning → FALSE

  Every single SLEEP_STAGE row fails the filter. getPendingSleepStages() returns
  an empty list every sync.

  Consequently: byDate is empty (SleepStagePromoter.kt:54), the for ((date, 
  stages) in byDate) loop never executes (SleepStagePromoter.kt:84), zero rows
  are written to sleep_sessions or sleep_stages, promote() returns
  SleepPromotionResult(datesProcessed=[], stagesInserted=0, sessionsCreated=0, 
  errors=[]) without any exception — so the call site in process() sees a clean
  return and cannot detect the failure.

  The table has a created_at column (MetricReadingStagingEntity.kt, column
  created_at), set to Instant.now() at parse time (WasmDriverEngine.kt:123: val 
  now = Instant.now()). created_at is the time the row was inserted during the
  current sync session — which IS within the sync window. Filtering by
  created_at would correctly find historical sleep data staged during this sync.
  Filtering by recorded_at does not.

  No try/catch in promote() swallows this. The empty result is not an exception.
  The early-return is the if (pendingRows.isEmpty()) { /* byDate stays empty */
  } implicit path — perfectly silent success with zero side effects. The errors
  list remains empty.

  ---
  Conclusion

  The most likely current root cause is a third bug, distinct from both 
  previously-fixed bugs: the getPendingSleepStages SQL query in
  MetricReadingStagingDao (MetricReadingStagingDao.kt:177–192) filters by
  recorded_at >= :startMs AND recorded_at < :endMs, where startMs/endMs are the
  live BLE sync session timestamps. SLEEP_STAGE readings have recorded_at set to
  the historical sleep epoch-ms (the actual time the sleep occurred, decoded
  from the device's BCD timestamp), which is always hours before the sync
  session starts. The filter excludes 100% of sleep stage rows on every sync.
  SleepStagePromoter.promote() receives an empty list, exits silently, writes
  zero rows to sleep_sessions and sleep_stages, and the DailySummaryWorker
  consequently finds no session and writes sleepMinutes = null.

  This is not a call-ordering race (Bug 1 — fixed in both
  dispatchPostStreamParse() and triggerSync()). It is not a timezone mismatch
  (Bug 2 — the promoter now correctly uses ZoneId.systemDefault()). It is a
  time-domain mismatch: the query predicate column (recorded_at, representing
  when sleep occurred) is being compared against a sync-session timestamp
  (representing when the device was connected), and these two time domains never
  overlap because the device transmits historical data. The staging entity has
  a separate created_at column that correctly represents when the row was
  inserted during this sync session; the query should use that column instead.
