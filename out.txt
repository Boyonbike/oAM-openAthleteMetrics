● HRV + Baseline System Audit

  I read every file touched by this work (migrations, calculator, baseline
  repos, worker, UI) directly against the code — no assumptions. Full findings
  were filed via ReportFindings (7 items); here's the complete picture organized
  by your 7 headings, including what checked out clean.

  1. Schema Migration (morning_hrv_ms → overnight_hrv_ms)

  Clean. morning_hrv_ms is gone from DailySummaryEntity, DailySummary, and all
  DAOs/ViewModels — the only surviving references are historical comments in
  AppDatabase.kt and the seeder's morningHrv variable name (see §7). avg_hrv_ms
  is untouched — still computed independently from all-day HRV readings in
  DailySummaryWorker. MIGRATION_15_16 correctly recreates the table (SQLite
  can't DROP COLUMN pre-3.35.5), copies every column except mapping old
  morning_hrv_ms values to NULL (not reinterpreted), and is registered in
  DatabaseModule's .addMigrations(...) chain with version bumped to 18. Verified
  against the exported 16.json/18.json schemas.

  2. Overnight HRV Calculation

  Clean. OvernightHrvCalculator executes exactly: session lookup → null if none
  → window query using session.sleepStartMs/sleepEndMs (not calendar-day) → <3
  readings → null → 10–250ms filter → <3 after filter → null → mean.
  DailySummaryWorker calls overnightHrvCalculator.calculate(date)
  unconditionally on every run (no skip-if-exists), correctly supporting
  out-of-order sync.

  3. Baseline Repository

  Mostly clean, one real deviation:
  - BaselineEntity/BaselineDao/BaselineRepository all exist and compile against
  BaselineMetric (dedicated enum), not MetricType. MetricType has no SLEEP
  value; MetricRouter's when-blocks are untouched (verified full diff-equivalent
  read).
  - Finding: no explicit MetricType → BaselineMetric mapping exists anywhere —
  DailySummaryWorker just loops BaselineMetric.entries and recalculates all six
  every run (see reported finding).
  - BaselineMetric.SLEEP sources from summary.sleepMinutes (which itself derives
  from sleep_sessions.durationMinutes via the worker) — correct, not a
  metric_readings path.
  - 14-day-style minimum gate (values.size < minDays) is checked before any
  upsert, and returns early leaving any existing row in place — correct.
  - mean/stdDev/lower/upper formulas correct; windowDays on the entity reflects
  the actually-resolved window, not a hardcoded default. (Minor note: stdDev is
  population, not sample — flagged as informational only.)
  - setManualOverride/clearManualOverride are true stubs — both throw
  NotImplementedError, no storage logic crept in.

  4. Per-Metric Window/Minimum Overrides

  Clean. Table/DAO/repository exist; resolution order is exactly override row →
  BaselineFallbackDefaults → global SettingsRepository/fixed 14. HRV resolves to
  window=60/minimum=15 via the fallback map, not a hardcoded value in
  BaselineRepository. No Settings UI exists (setOverride/clearOverride are
  unused by any screen — confirmed by grep).
  BaselineEntity/BaselineWindowConfigEntity both carry a TODO for export/import
  inclusion.

  5. Daily Detail HRV Section

  Clean, except a missing TODO comment (see reported finding). HrvSectionState
  has exactly three distinct, visually distinct states (NoSleepSession → "No
  sleep session recorded", InsufficientData → "Not enough overnight data",
  HasData → headline + baseline). Graph/list use unfiltered raw readings queried
  directly against sleep-session timestamps
  (hrvRepo.getReadingsInRangeOnce(sleepStartMs, sleepEndMs+1)), independent of
  the filtered headline number. Baseline line hides correctly via ?.let{} when
  null. The "disabled in Settings" TODO the spec calls for does not exist
  anywhere in the file.

  6. Dashboard HRV Card

  Clean, with two notes filed. HR/RHR/Sleep/SpO2/Steps composables are untouched
  (git diff on MetricWidget.kt shows only the two Hrv -> value-accessor lines
  changed, a required compile fix, not new behavior). The HRV card's
  baseline-range text occupies the same layout slot other cards use for trend
  (parts.baselineText in the same Text position as uiState.trend?.label), and
  correctly never attempts a directional arrow on a range. The mini graph
  queries the same unfiltered sleep-window data as Daily Detail and is a plain
  value-index sparkline (not a 7-day trend) since it's fed from session-window
  readings, not getSummariesForRange. Tapping opens Daily Detail's
  cardiovascular section at the selected date — consistent with every other
  metric card (not a regression, just worth confirming this was the intended
  "History" destination). Filed: dead WidgetType.Hrv branches left behind in
  MetricWidget.kt's ViewModel now that HrvMetricWidget fully owns that type.

  7. Cross-Cutting

  - Coroutine safety: clean. Every new/touched DB call is suspend or Flow; no
  runBlocking found outside tests; the one new direct AppDatabase call

  - Hilt: clean. OvernightHrvCalculator, RoomBaselineRepository,
  RoomBaselineWindowConfigRepository, HrvMetricWidgetViewModel all have

  via @Binds in DatabaseModule; both new DAOs have @Provides methods.
  - Naming: SeederService.kt still uses morningHrv as a variable/parameter name

  - Bonus finding not in your list: HistoryViewModel.extractWearableValue
